# wom-buzz-watch

「クチコミ投資法」(SNSでバズった商品を早期に見つけて投資する手法)を自動化するボット。
ウォッチリスト企業の「業績にプラスの影響を与えうる新着情報」(新商品・新店舗・新業態・
新販路・コラボ等)を自動検知し、Google Trends・X(Yahoo!リアルタイム検索経由)の
話題の急上昇を検知したらDiscordに通知する。

## Tier構成

- **Tier 1(深掘り監視、本リポジトリの現在の実装)**: 少数の企業を対象に、
  公式サイトの新商品・ニュースを自動巡回し、新商品ごとに個別キーワードで
  Google Trends・X投稿頻度を追跡する。精度重視。
- **Tier 2(広く浅く監視、登録進行中)**: ~300社規模を対象に、社名+主力ブランド名を
  キーワードとして月1回ペースでローテーション監視する(1日10社ずつ)。速度より
  網羅性重視。`news_source`(個別サイトの新着ニュース巡回)は設定せず、EDINET DB
  連携による主力ブランド名の自動発見とGoogle Trends/Yahoo!リアルタイム検索の
  定点観測のみを行う(新商品の即時検知はTier 1のみ)。時価総額2000億円以下の
  上場企業を対象に、初回登録はClaude Code Pro契約時間を使って手動でスクリーニング・
  キーワード選定を行っている(運用中のAnthropic API従量課金を温存するため)。

## 主力事業・ブランド名の自動発見(EDINET DB連携)

新着ニュースの自動巡回だけでは、その企業の「主力事業・すでに存在する稼ぎ頭ブランド」を
見逃す(例: 共和コーポレーションの主力はスクイーズではなく、アミューズメント施設
「アピナ」だった)。これを補うため、[EDINET DB](https://edinetdb.jp) の無料APIを使い、
有価証券報告書の「事業の内容」全文をClaude APIに読ませて、業績インパクトが大きそうな
事業・ブランド名を自動抽出し、`base_keywords`に永続的に追加する。

- 「事業の内容」だけでは一般的な表現(「アミューズメント施設運営事業」等)に留まり、
  消費者向けの通称ブランド名(「アピナ」「iBLOOM」等)が出てこないことが分かったため、
  **「沿革」セクション**(店舗の出店履歴を実名の年表で語ることが多い)と、
  **`homepage_url`で指定した公式トップページの外部リンク一覧**(持株会社的な
  企業のトップページはブランドサイトへの導線をバナーで並べていることが多い)も
  合わせて読ませている。この組み合わせで、共和コーポレーションの
  「アピナ」「MOOOSH」「iBLOOM」「トレーディングカードピット」を
  **新規登録シミュレーション(既存の手動登録キーワードなし)で全て自動発見**できることを
  確認済み。
- 各社の`latest_fiscal_year`(最新の有報の年度)を記録し、**前回チェック時から変わって
  いなければ再抽出をスキップ**する(有報は年1回程度しか更新されないため、毎月同じ
  文章を読み直す無駄を避けている)。通常の新着ニュース巡回(RSS/HTML)は既存の頻度通り
  毎回実行される — スキップされるのはEDINET DB連携部分のみ。
- 発見したキーワードは`state/segment_keywords.json`に保存し、新商品ニュース由来の
  キーワード(直近6件までしか保持しない)とは違って**永続的に**追跡され続ける。
- プロンプトは「一般名詞っぽく聞こえるか」ではなく「その言葉で検索した時にこの企業の
  話題が中心にヒットするか」を判定基準にしている。「3Dアイス」のような、普通の単語の
  組み合わせでもこの企業固有の商品名であれば含め、「バッティングセンター」のような
  業界共通の施設・カテゴリ名は除外する。

必要なSecrets: `EDINETDB_API_KEY`([edinetdb.jp/developers](https://edinetdb.jp/developers)
で無料登録、100回/日まで無料)。300社規模でも月間数百回程度の利用に収まり、
追加のClaude API費用も月1ドル未満の見込み。

### 既知の限界: 登録前に発生し、かつ既に流れてしまった過去のバズ

「事業の内容」「沿革」「公式サイトのトップページ」のいずれにも載らず、かつ企業の
ニュース一覧ページからも既に流れてしまった**過去の**商品ローンチ(例: ジェリービーンズ
グループの「3Dアイス」— 2025年11月発売、現在のtopicsページには残っていない)は、
上記の自動化だけでは原理的に発見できない。

これへの対応として、**企業を新規登録する時だけ**、直近1年分の「話題になった商品」を
Web検索で一度確認し、見つかれば`base_keywords`に手動で追加する。これは月次の自動
処理には組み込まない(登録時の1回限りの作業)。**登録後に新しく発売される商品は、
通常の新着ニュース巡回がリアルタイムで検知するため、この限界の対象外。**

## 実行頻度とローテーション

cron-job.orgからの起動自体は毎日20:00(JST)だが、各企業を毎日チェックするわけではない。
`state/last_checked.json`に企業ごとの最終チェック日を記録し、**前回チェックから30日
以上経過した企業のみ**を対象に、1回の実行で**最大10社まで**処理する
(`CHECK_INTERVAL_DAYS` / `MAX_COMPANIES_PER_RUN` で調整可能)。

これにより、今は3社なので実質「毎日→ほぼ月1回チェック」の頻度になり、将来
ウォッチリストが300社規模になっても「1日10社ずつ処理→全体で月1周」という
負荷が一定のローテーションにそのまま拡張できる。cron自体は将来も毎日起動のままで良く、
このゲーティングロジックだけが対象社数のスケールに応じて頻度を自動調整する。

## 仕組み(Tier 1)

1. 毎日 [cron-job.org](https://cron-job.org) から GitHub Actions の `workflow_dispatch` を呼び出す(上記の通り実際に処理するのは月1回×対象企業のみ)
2. `config/watchlist.json` の各企業について:
   - 公式サイトの新商品・ニュース一覧(RSSまたはHTML)を巡回し、新着を検知
   - 新着タイトルをClaude API(Haiku)に渡し、「新商品/新店舗/新業態/新販路/コラボ/
     その他」のいずれかに該当する業績インパクトが期待できる内容かを判定
     (決算・人事・定型連絡等は除外)。該当すれば検索キーワードを抽出して追跡対象に追加
     (直近6件まで。ANTHROPIC_API_KEY未設定時は簡易ヒューリスティックにフォールバック)
   - 社名 + 追跡中の商品キーワードそれぞれについて
     - **Google Trends**(非公式・内部APIを直接叩く方式。日本語検索の関心度を0-100で取得)
     - **Yahoo!リアルタイム検索**(X/旧Twitterの投稿を検索できる無料サービス。
       投稿の時間間隔から「投稿頻度(件/時)」を逆算し、Xの投稿ボリュームの代理指標として使う)
   - 直近28日の中央値を基準に、急上昇(Trends: 2.5倍以上 or +40pt、X頻度: 3倍以上)を検知
3. 新商品検知・急上昇検知があればDiscordに通知
4. 状態(既知ニュース・追跡キーワード・日次履歴)を `state/` にコミットして保存

## なぜX/TikTok/Instagramの公式APIを使わないのか

- **X API**: 2026年に無料枠が廃止され、現在は完全従量課金制($5/1000件読み取り)
- **TikTok API**: Research APIは学術機関限定・商用利用禁止。一般公開APIにトレンド検索機能はない。
  ヘッドレスブラウザでの検索ページ取得も試したが、ログイン/CAPTCHA要求で弾かれることを確認済み
- **Instagram API**: 自社ビジネスアカウントの投稿管理用であり、他者の投稿やハッシュタグの
  世間トレンドを横断的に検索する用途には使えない

そのため、Google TrendsとYahoo!リアルタイム検索(X代替)という2つの非公式だが実際に
動作を確認した無料の手段を採用している。

## セットアップ

```bash
pip install -r requirements.txt
python scripts/buzz_watch.py --dry-run  # ローカルで動作確認
```

GitHub リポジトリの Secrets に以下を設定する:

- `DISCORD_WEBHOOK_URL`: 通知先のDiscord Webhook URL
- `ANTHROPIC_API_KEY`: 新商品タイトルからのキーワード抽出精度を上げるため(任意。
  未設定でも簡易ヒューリスティックにフォールバックして動作する)。
  [console.anthropic.com](https://console.anthropic.com/) でキーを発行する。
  Haikuモデルを使うため実費は月数十円〜百円程度の見込み。

cron-job.orgでの毎日実行設定は [monthly-yoy-watch](https://github.com/rimpeinishihara-cell/monthly-yoy-watch) と
同じ手順(fine-grained PAT発行 → workflow_dispatchをPOSTで叩くジョブ作成)。

## 新着ニュース巡回の設定方法(`news_source`)

`config/watchlist.json`の各社`news_source`は3種類の`type`に対応している。

- `rss`: 標準的なRSS/Atomフィード(`<item>`タグ)をそのまま使う。一番手軽で壊れにくい。
- `html_regex`: RSSがないサイト向け。企業ごとにPython関数を書く代わりに、
  `url`とニュース一覧の1件ぶんにマッチする正規表現`pattern`をJSON側に書くだけで
  動く汎用パーサー(`fetch_html_regex_news()`)。`pattern`は名前付きグループ
  `url`(必須)・`title`(必須)・`date`(任意)を持つ正規表現文字列で、
  `re.finditer(pattern, html, re.S)`でマッチした分だけニュース項目として扱う。
  相対URL(`/xxx`や`../xxx`)は自動的に絶対URL化され、サイトのエンコーディング
  (Shift-JIS等)も自動判定される。
- `html_list_ibloom` / `html_list_jbg`: ごく初期に個別サイト向けに書いた
  専用パーサー(共和コーポ・ジェリービーンズグループ用)。新規追加では
  基本的に`html_regex`を使えばよく、これらのような専用関数は増やさない方針。

45社中24社(2026-09-09時点)に`news_source`を設定済み。残り21社は以下の理由で
未設定(いずれも`base_keywords`によるTrends/Yahoo急上昇検知そのものは機能する。
新商品の即時検知だけができない状態):

- サイトがVue/Next.js等のSPAで、ニュース一覧がHTMLに直接出力されずJSで
  描画される(ANYCOLOR、RIZAPグループ、ガンホー、カンロ等) → ヘッドレス
  ブラウザかサイトのJSON API調査が必要
- `requests`ライブラリからのアクセスがWAFに403でブロックされる(壽屋) →
  ボット判定の回避はしない方針のため保留
- ニュース一覧ページがIR/決算開示のみで、消費者向け製品ニュースがそもそも
  存在しない(コモ、六甲バター、リヒトラブ等)
- 候補ページの構造調査が完了していない(ベリテ、千趣会、I-ne、新日本製薬、
  エステー、Hamee、エスビー食品、ブルボン、ほぼ日、アートネイチャー、
  コラントッテ、モロゾフ)

## 既知の制限

- Google Trends・Yahoo!リアルタイム検索はいずれも非公式手段(内部APIの直接叩き)であり、
  サイト側の仕様変更で突然動かなくなる可能性がある
- 新商品の自動検知は、企業公式サイトのニュース一覧ページの構造に依存する。
  `html_regex`方式でも、サイトがSPAだったりWAFでブロックされたりすると
  対応できないケースがある(上記参照)
- キーワード抽出はニュースタイトルからの簡易ヒューリスティックであり、
  店舗イベント情報なども誤って追跡対象に混ざることがある(実害は小さいが精度に限界あり)
- Yahoo!リアルタイム検索の「投稿頻度」は検索結果ページ(最大40件程度)の時間分布からの推定値であり、
  正確な投稿数そのものではない
